# 版本从哪来

有三样东西都叫版本，指的不是同一个对象。混用一次，标题、包名和索引就会各说各的。

## 1. 三个身份

| 身份 | 写在 | 决定什么 | 谁改 |
| --- | --- | --- | --- |
| tag | 仓库的标签，也就是版本号 | 发布标题的版本号、正文的提交区间、Release 挂在哪 | 维护者 |
| ROM 版本 | 运行时仓库配置文件里的默认版本项 | 包名、包内自述里的版本、索引里的 ROM 版本 | 维护者 |
| APK 版本 | 宿主工程 app 模块的版本号与版本名 | APK 自己的身份 | 维护者 |

三者对得上的是它们指向同一个提交，不是同一串字符。同一个 tag 打出来的包，包名里的版本来自配置文件，标题里的版本来自 tag，两者本来就可以不同。发布页的标题因此不该被当成产物版本的来源，产物名也不该被当成发布版本的来源。

## 2. 包与配置必须说同一个版本

正文脚本与索引脚本都会读打包报告里的 romKey，并要求两件事同时成立。romKey 里的 id 与配置文件里的 id 相同，romKey 里的版本与配置文件里的默认版本相同。

任一处不成立就退出，不发布。包名由打包器按 romKey 生成，如果配置文件在打 tag 之后被改过而没有重新构建，发出去的包会带一个仓库不承认的版本，而下载的人只会看文件名。

## 3. 标签的形状是硬条件

发布只接受三段点分数字的标签，也就是 `v` 加三组数字、用点隔开。仓库里已经有过形如 `v1.0.0-a9-boot-20261112` 的构建标记标签，它是给装机对照用的，不是版本号，第一道闸门会直接拒绝它。这类标签继续用来标记一次可开机状态没有问题，只是不要指望它能发布出 Release。

要发布那一版，就在同一个提交上再打一个三段点分数字的标签。两个标签指向同一个提交，打出来的包内容相同，只有运行时 tar 包的名字随标签变，区别只在标签是身份还是标记。

## 4. 本地覆盖版本

构建脚本允许在命令行覆盖 ROM 版本，用于本地试验。CI 不设这个开关，所以 CI 产物名必须等于配置文件里的默认版本。

用覆盖版本打出来的包不能走发布，闸门会拒收。这是期望行为，因为本地试验包没有经过 CI 的构建与产物校验，它的哈希也不在任何一次发布记录里。

## 5. 改版本的纪律

版本号是对外身份。改了之后，历史日志、实例目录与导出证据全都对不上号。改配置里的默认版本或者打一个新 tag 都属于发版动作，单独一轮、单独说明理由、可以整体回滚。

已经发布过的记录不要手改。索引、发布页与下载过的包三处要能互相解释，手改一处等于把它们拆开。

## 6. 判据

三条命令分别读配置文件、包内自述与索引，值必须互相解释得通。

```bash
sed -n 's/^defaultRomVersion: *//p' rom/rom.properties.yaml
unzip -p dist/versebox-android9-<ROM 版本>.zip versebox_properties.yaml | grep -E '^(id|romVersion|apiLevel):'
node -e "const e=require('./release/release.json'); console.log(e.at(-1).version, e.at(-1).romVersion)"
```

包名里的版本等于配置文件里的默认版本，包内自述的版本等于包名里的版本，索引最后一条的版本是 tag 的版本段。
