# 发布流水线

这一篇说明两件事：哪个工作流负责构建，哪个负责发布，以及发布失败时该看哪一行。

## 1. 为什么是两个工作流

构建回答的是这份源码能不能被别人重建成一样的产物。发布回答的是这次发出去的文件有没有经过校验。两条判据的代价不同，构建红了只是这一版不能用，发布错了却会直接出现在公开页面上，删掉之后时间线里仍然留着痕迹。

两件事仍是两个工作流，但之间有一条自动的接力：标签构建成功之后，发布工作流由构建的完成事件直接拉起，不需要任何人手动调用，也不需要额外令牌。构建失败或者不是标签构建时，发布工作流会停在入口条件上，连第一道闸门都不会进。

## 2. 两个工作流各管什么

| 工作流 | 触发 | 产出 | 权限 |
| --- | --- | --- | --- |
| `.github/workflows/build.yml` | 任意分支推送、拉取请求、推送 tag、手动触发 | 运行时的 tar 包、ROM 包、最小占位包、常驻原生库、打包报告，以及这些文件的哈希清单，统一上传成名为 `a9-runtime` 的附件 | 只读 |
| `.github/workflows/release-publish.yml` | 标签构建成功后自动开始，也可以手动触发并填一个标签与一个是否试跑的开关 | GitHub Release，以及索引文件里的一条记录 | 写仓库内容，读 Actions 记录 |

构建工作流只读是刻意的。它要做的判断只有"这份源码能不能编出产物"，给它写权限等于让一次构建有能力改默认分支。发布工作流要写仓库内容，因为它要把索引写回默认分支，但它没有任何一条路径会重新打包，取的是那次构建上传的附件。

## 3. 什么事件会跑什么

| 事件 | 构建 | 发布 |
| --- | --- | --- |
| 推送分支，改动不在索引目录 | 全量构建 | 不运行 |
| 推送分支，改动只在索引目录 | 跳过 | 不运行 |
| 推送一个标签 | 全量构建 | 构建成功后自动开始 |
| 拉取请求 | 全量构建 | 不运行 |
| 手动触发发布 | 不构建 | 发布指定标签 |
| 手动触发构建 | 全量构建 | 不运行 |

索引目录的跳过规则是给发布收尾准备的。发布工作流把索引写回默认分支，这次提交只改 `release/release.json`，重跑一遍构建没有意义。

## 4. 发布工作流按什么顺序做事

| 步骤 | 做什么 | 失败时先看什么 |
| --- | --- | --- |
| 检出 tag | 取这个 tag 的完整历史与标签，正文要用它算区间 | 报浅克隆说明检出深度没设成零 |
| 装 Node | 给三个脚本准备运行时 | 报找不到 node |
| 第一道闸门 | 确认标签存在，并且就是三段点分数字的版本号 | 报错行里带标签原文 |
| 第二道闸门 | 确认这个 tag 上有一次成功的构建 | 日志会列出同一提交上的全部运行，以及各自的名称与结论 |
| 取附件 | 按那次运行的编号下载构建上传的附件 | 报附件不存在，多半是超过保留期 |
| 第三道闸门 | 确认文件齐全，并逐个对上哈希清单 | 报哪个文件的哈希对不上，或哪一组通配符一个文件都没匹配到 |
| 第四道闸门 | 让打包器重读 ROM 包内的清单 | 打包器列出的问题条目 |
| 收集附件 | 算出每个附件的哈希与字节数，并给出发布用的文件清单 | 报零字节、缺文件，或同一个文件被两条通配符同时匹配 |
| 生成正文 | 写出正文、标题与版本三个文件 | 报区间、版本或打包报告不一致 |
| 写索引 | 按 tag 覆盖写入一条记录 | 报索引里有不符合格式的旧条目 |
| 试跑 | 打印标题与正文，不发布 | 这一步的内容就是正式发布的内容 |
| 发布 | 建或更新 Release，正文用上一步的文件 | 报附件没匹配上，说明前面漏了文件 |
| 写回索引 | 把索引提交到默认分支 | 看推送与变基的重试记录 |

第二道闸门的判据是 tag 名字，不是提交号。同一个提交常常同时有一次分支构建和一次 tag 构建，两者打包出来的文件名不同，发布必须带 tag 那一次的文件。判据因此写成提交号与名称同时相等。

第三道闸门的四条通配符各自对应一组必带的文件，运行包、ROM 包与最小占位包、常驻原生库、打包报告。少一组就说明那次构建没有走到那一步，此时应该回去看构建，而不是把发布补完。

## 5. 并发与超时

构建工作流的并发组带上分支或标签名，同一目标的新推送会取消上一次，因为旧的那次产物已经没有意义。发布工作流的并发组只有一个名字，并且不允许取消已在运行的那一次，同一个 tag 连点两次时第二次排队，第一次写完索引第二次读到的是写完的版本，不会出现两次都在追加。

构建超时四小时，这个数值由镜像下载与原生层编译决定，缓存命中后会短很多。发布超时九十分钟，下载产物加对一两个 GB 的包算哈希需要几分钟，余量留在这里。超过九十分钟说明在重算不该重算的东西，先看是不是又在本地打了一遍包。

## 6. 产物各是什么

| 文件 | 是什么 | 谁消费 |
| --- | --- | --- |
| 运行时的 tar 包 | prepared 树 | 第三方复现运行时 |
| ROM 包 | 客体内容与自述 | 宿主导入 |
| 最小占位包 | 只声明支持这个系统 | APK 内声明 |
| 常驻原生库的 tar | APK 侧必须带的原生文件 | APK 打包 |
| 打包报告 | 载荷哈希、文件数、承载方式 | 追溯这个包怎么来的 |
| 哈希清单 | 上面全部文件的哈希 | 下载后的校验入口 |

包名里的版本来自本仓库的配置文件，与标签无关，见[04-VERSION-SOURCES](04-VERSION-SOURCES.md)。
