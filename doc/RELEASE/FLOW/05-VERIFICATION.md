# 验证与发布操作

这一篇说明四件事：这些改动交付前跑过什么，本轮改动了哪些行为，还有什么没有验证，以及维护者发布一次要按什么顺序操作。

## 1. 交付前跑过的检查

四条检查都在本机跑过，用的夹具建在系统临时区，不放仓库里，也不动本仓库的任何标签。脚本留在宿主工程的 `_bin/a9/scratch/ci-verify/`，不入库。

### 1.1 四个脚本的语法

四个脚本都是 ES 模块，用 Node 自带的语法检查即可，正常时没有任何输出。

```bash
node --check .github/scripts/collect-release-assets.mjs
node --check .github/scripts/generate-release-notes.mjs
node --check .github/scripts/update-release-index.mjs
node --check .github/scripts/lib/release-facts.mjs
```

四个文件都通过。

### 1.2 两份工作流的 YAML 与结构

用真正的解析器读一遍，比只看缩进可靠。解析通过之后还要断言结构，一共十八条，覆盖这些事实：构建工作流只读、推送触发带索引目录的跳过规则、构建工作流里不再有任何发布步骤、上传的附件名是 `a9-runtime`、发布工作流由构建完成事件接力、手动触发只有两个输入、发布步骤排在写索引之前、第四道闸门排在收集附件之前、正文路径与附件清单都指向生成的文件。

```bash
python -c "import yaml,sys; [yaml.safe_load(open(p, encoding='utf-8')) for p in sys.argv[1:]]" \
  .github/workflows/build.yml .github/workflows/release-publish.yml
```

十八条断言全部通过。

### 1.3 每个步骤里的 shell

YAML 解析只证明缩进合法，不证明里面的 shell 能读。做法是把每个步骤的命令块单独落成文件，逐个用 shell 的语法检查跑一遍。两份工作流一共十七个 `run` 块，十七个都通过。

```bash
bash -n <步骤块文件>
```

### 1.4 用夹具跑三个脚本

夹具里造两个标签，区间中间放两条提交，标签之后再放一条提交，然后按真实顺序跑收集、正文、索引三个脚本，二十七条断言全部通过。

| 行为 | 判据 |
| --- | --- |
| 收集脚本输出四项附件，名字是相对路径且用正斜杠 | `release-assets.json` 的 `name` 字段 |
| 字节数与 sha256 与文件一致 | 逐项与 `stat` 结果比对 |
| 零字节文件被拒收 | 非零退出，报"零字节" |
| 同一个文件被列两次被拒收 | 非零退出，报"列了两次" |
| 标题由固定前缀与标签拼成 | 标题文件等于前缀加标签 |
| 区间只含上一个标签到本标签的提交 | 正文里没有标签之后那条提交的标题 |
| 提交标题里的星号与下划线被转义 | 正文里出现反斜杠转义后的原文 |
| 发布版本与 ROM 版本各占一行 | 正文里两者分别出现，且不是同一个值 |
| 载荷哈希与文件数来自打包报告 | 正文里出现报告里的值 |
| 四个附件都列在正文的产物一节 | 附件行数与清单条数相等 |
| 给出完整变更链接 | 正文带 `/compare/<上一个>...<本标签>` |
| 第一个标签时说明没有可比较的上一个版本 | 正文给说明，且没有完整变更链接 |
| 同一个版本重发只留一条并覆盖内容 | 两次写入后条目数仍为一，标题是第二次的值 |
| 换一个版本再发 | 条目数变为二，最后一条是新的版本 |
| 旧版本补发后排到末尾 | 条目数不变，最后一条是补发的那个版本 |
| 已有一百条时新增一条 | 条目数仍为一百，最早的那条消失 |
| 校验清单不进附件列表 | 一条记录里附件比清单少一项 |
| 版本写成数字 | 脚本非零退出并提示手改 |
| 版本参数不是三段点分数字 | 脚本非零退出并说明格式 |
| 打包报告与配置不一致 | 脚本非零退出并说明要重建这个标签 |

### 1.5 按真实顺序执行步骤本体

最后一步不重写脚本，而是把工作流 YAML 里 `run` 块的原文件抽出来，在夹具里按真实顺序执行：先跑构建工作流的打包步骤，再跑发布的四道闸门、收集、正文、索引与试跑，十八条断言全部通过。

其中三条是这次故意造坏之后再跑的，用来证明闸门真的会拦：

| 造坏的方式 | 期望 | 结果 |
| --- | --- | --- |
| 往 ROM 包里追加几个字节 | 第三道闸门报哈希不一致 | 拦下 |
| 删掉常驻库 tar | 第三道闸门报出缺的那一组通配符 | 拦下 |
| 同时放两个完整 ROM 包 | 第四道闸门报期望恰好一个 | 拦下 |

第四道闸门里的打包器调用在夹具里用桩代替，因为夹具里没有真包可校验。真包上的那条校验由构建工作流的 ROM 包自检负责，那一步跑的是 `rom/pack-rom.py --verify-only`。

## 4. 发布一次的操作顺序

正常一次发布只有三步。

1. 提交并推送改动，确认工作区干净。
2. 打一个三段点分数字的标签并推送，标签就是版本号。
3. 等两条运行都变绿，构建先开始，构建成功后发布自动接力。

结束后核对三处。发布页的标题是产品前缀加标签，正文里的哈希与附件列表一致、附件齐全，默认分支上索引多了一条。

需要人工重新发布时才用第二条路，比如补发一个旧版本，或者上一次发布中途失败。这条路走手动触发，填同一个标签，先打开试跑开关读一遍标题与正文，确认无误再关掉开关跑一次。手动触发与自动接力走的是同一套闸门与同一份正文生成代码。

## 5. 失败先看哪里

| 现象 | 先看 |
| --- | --- |
| 第一道闸门报标签形状不对 | 标签是不是三段点分数字，构建标记类标签不能发布 |
| 第二道闸门报没有成功的构建 | 日志列出同一提交的运行，看名称与结论 |
| 第三道闸门报某一组通配符一个都没匹配到 | 那次构建的打包与上传步骤，看是不是少产了一件 |
| 第三道闸门报哈希不一致 | 是哪个文件，以及那次构建是否被重跑过 |
| 第四道闸门报打包器错误 | 打包器列出的问题条目，回查打包脚本 |
| 正文脚本报浅克隆 | 检出的深度是否为零 |
| 正文脚本报版本不一致 | 配置文件是否在打标签之后改过而没有重新构建 |
| 发布成功但索引没动 | 写回索引那一步的推送与变基记录 |
